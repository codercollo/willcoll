D. MIGRATION ORDER — small steps, tests green after each
================================================================================
1. Split shared vs rentals
   Carve internal/shared/{ledgerkit,reconcile,httpx,auth,jobs,exportx,pdf,
   payhero,sms,mailer,validator,jsonlog,vcs} out of today's internal/data,
   internal/db, cmd/api, and internal/{reconciliation,payhero,pdf,mailer,sms,
   validator,jsonlog,vcs}. No behavior change — pure extraction. Rentals
   imports from internal/shared instead of its own package. Tests green
   with zero product-behavior diffs.

2. Rename cmd/api to cmd/rentals-api
   Mechanical rename, update Makefile targets (run/api -> run/rentals-api,
   keep run/api as a deprecated alias until step 4 removes it), Dockerfile
   build path, CI job. Still one database, one Postgres role pair.

3. Platform DB + module entitlements
   Stand up willcoll_platform; move managers, staff (new), admins,
   sessions, tokens, subscriptions, subscription_plans/invoices into it,
   renumbered as backend/migrations/platform/. Add manager_modules,
   payment_channels, payment_inbox, service_links, handoff_invoices (the
   last two are empty until step 7's cross-product handoff work, but the
   tables exist now so RLS/grants land once). rentals-api gains a
   requireModule("rentals") check. Dual-write or a one-time backfill
   migrates existing manager rows.

   Cross-database FK drop: willcoll_rentals' tenant_id columns currently
   FK to managers(id) in the same database. Once managers moves to
   willcoll_platform, that FK is impossible (no cross-database FKs,
   system-design.txt Part E.3) — tenant_id becomes a plain uuid column in
   willcoll_rentals, validated only at the application layer against
   platform.managers.

   Cut-over sequence: full backup of willcoll (pre-split) immediately
   before cut-over; backfill willcoll_platform from it; drop the old
   platform-owned columns/tables from willcoll_rentals only after an RLS
   isolation test passes — a test proving one manager's session still
   cannot read another manager's rows now that tenant_id is an unenforced
   plain column, not an FK-backed one. See docs/adr/0006-platform-
   database-split.md for the FK-drop rationale.

4. Split CI/deploy
   test.yml gains the per-product job-matrix dimension. _deploy.yml
   becomes the shared reusable workflow; rentals-staging.yml and
   rentals-production.yml get real content and start deploying. Remove
   the run/api and build/api Makefile aliases from step 2.

5. Estates P0
   New willcoll_estates database, backend/migrations/estates/000001+,
   internal/estates/{data,db,pdf}, cmd/estates-api. Build in the order
   system-design.txt Part C lists P0 in: estates/blocks/units/owners +
   CSV import + opening balances, then budget apportionment, then
   invoicing, then pay + reconciliation, then reports/exports. Each
   sub-step lands with its own tests before the next starts.

6. Waste
   New willcoll_waste database, backend/migrations/waste/000001+,
   internal/waste/{data,db,pdf}, cmd/waste-api. Deliberately smaller than
   Estates: one ledger type (SERVICE_FEE), no owners/committee layer.
   Reuses shared/ledgerkit and shared/reconcile as-is — the reconciliation
   logic doesn't change, only the schema it points at.

7. Estates P1
   Owner/committee portal, maintenance requests (closing one posts an
   expense — reuses shared/ledgerkit's posting path), notices, committee
   approvals, vendors, clearance certificate. Cross-product handoff
   (service_links, handoff_invoices) is exercised for real here for the
   first time, once a collector can link to both a rentals property and
   an estate.
